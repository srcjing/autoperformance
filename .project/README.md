# 设计文档目录（.project）

本目录是本项目（auto_performance，性能测试平台）唯一的设计文档根目录。所有需求、方案、原型、决策与安全设计均沉淀于此，随代码仓库一起纳入版本管理，作为“设计事实源”。

## 目录结构

```
.project/
├── README.md            # 本文件：目录说明 + 归档/修订约定
├── CHANGELOG.md         # 设计变更归档记录（每次功能实现或变更后更新）
├── prds/                # 需求文档（PRD / 需求澄清 / 细节补充）
├── specs/               # 技术方案、架构、选型、结构图（项目结构 / 前端层级）
├── prototypes/          # 前端原型（参考业界案例）
├── decisions/           # 架构决策记录（ADR，含选型结论与备选）
└── security/            # 安全设计（STRIDE 等，后续补充）
```

> 说明：`security/` 目录在进入安全设计阶段时创建；`design/` 目录在需要正式设计系统资产（DESIGN.md 等）时创建。

## 文档类型与用途

| 目录 | 产物 | 读者 | 更新时机 |
| --- | --- | --- | --- |
| `prds/` | 需求文档、需求澄清记录、字段/实体清单、验收口径 | 产品 / 研发 / 测试 | 需求新增或变更时 |
| `specs/` | 架构设计、技术选型、系统/项目结构图、前端层级图、接口与数据流契约 | 架构 / 研发 | 方案设计或架构调整时 |
| `prototypes/` | 前端原型（静态 HTML / 可运行原型） | 产品 / 设计 / 研发 | 页面或交互变更时 |
| `decisions/` | ADR：`ADR-0001-主题.md` | 全员 | 做出/推翻关键决策时 |

## 归档与修订约定（重要）

本项目要求：**每次功能实现或变更之后，对设计文档进行归档或修正**。约定如下：

1. **设计先行**：任何功能开发前，先在 `prds/` 补需求、在 `specs/` 补方案，必要时在 `prototypes/` 补原型。
2. **变更即修正**：实现过程中若发现设计与实现不一致，**必须**回到对应文档修正设计，而不是只改代码。
3. **归档记录**：每次设计变更，在 `CHANGELOG.md` 追加一条记录，格式：
   - 日期
   - 变更类型（新增 / 修正 / 归档 / 废弃）
   - 涉及模块
   - 变更摘要
   - 关联文档路径（相对 `.project/`）
   - 关联提交（commit hash，可选）
4. **决策留痕**：关键技术选型或架构决策，写一份 `decisions/ADR-NNNN-主题.md`，记录背景、备选方案、结论与理由、影响面、撤销条件。
5. **单一事实源**：同一主题只保留一份“当前有效”文档；历史版本靠 git 历史回溯，不维护 `_v1/_v2` 副本。

## 文档命名规范

- PRD：`prds/PRD-<模块>-<主题>.md`（如 `PRD-环境管理-环境列表.md`）
- 方案：`specs/<主题>.md`（如 `specs/architecture.md`、`specs/frontend-structure.md`）
- ADR：`decisions/ADR-<4位序号>-<主题>.md`
- 原型：`prototypes/<页面或主题>/index.html`
