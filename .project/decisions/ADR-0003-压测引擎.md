# ADR-0003：压测执行引擎

- **状态**：已采纳（Accepted）
- **日期**：2026-10-26
- **决策者**：架构师
- **关联**：ADR-0001（后端）、ADR-0004（数据库）

## 背景

压测执行引擎是本平台的技术核心与关键决策点。需求要点：

1. 按"环境 + 接口范围 + 流程"编排压测，并输出结构化结果用于报告生成。
2. 接口有"预设关键指标阈值"，需在执行后做"达标评估"。
3. 强约束：离线部署、可移植、依赖自包含。

## 备选方案

| 维度 | 集成 k6 ✅ 推荐 | 集成 JMeter | Locust | 完全自研 |
| --- | --- | --- | --- | --- |
| 运行时 | Go 单二进制 | JVM（需内嵌 JRE） | Python 解释器 | 自研二进制 |
| 离线打包 | 单文件分发，体积小 | 体积大 | 需内嵌解释器 | 体积最小但开发成本高 |
| 脚本化/可维护 | JS 脚本（可版本化、可复用） | .jmx XML（难 diff/复用） | Python 脚本 | 自定义 DSL（需自建） |
| 协议覆盖 | HTTP/gRPC/WebSocket/browser 等 | 极广（插件多） | HTTP 为主 | 按需自建 |
| 结构化结果 | 原生输出 JSON（Summary + Metrics） | 需解析 JTL/聚合报告 | 可输出（需自建） | 自建 |
| 阈值/评估 | 支持 thresholds + 自定义 | 断言器 | 自建 | 自建 |
| 与 Go 后端集成 | 子进程 CLI + JSON 结果，契合 | 子进程 + JTL 解析 | 需打包 Python | 原生但成本高 |
| 开发/维护成本 | 低 | 低（但脚本难维护） | 低 | 极高 |

## 决策

**以 k6 为默认执行引擎，通过"子进程 CLI"方式集成；并设计"引擎适配层（Engine Adapter）"抽象执行引擎接口，为未来插拔预留空间。**

- 默认引擎：`k6`（官方二进制，随离线部署包分发）。
- 集成方式：后端 `engine` 模块生成 k6 脚本（注入环境变量、接口地址、并发/时长、阈值），通过 `exec` 拉起 k6 子进程，实时捕获 stdout 进度与最终 `--out json` 结果文件，解析后送入报告/评估管线。
- 阈值评估：优先使用 k6 的 `thresholds` 声明式阈值；同时后端做二次评估（以接口预设阈值为准），保证阈值口径统一、可追溯（见 `specs/architecture.md` 阈值评估数据流）。
- 自研引擎：**不作为首期默认**，仅当出现 k6 无法覆盖的私有协议/特殊场景时，作为 Adapter 的一个实现逐步补齐。

## 理由

1. **离线 + 单二进制**：k6 由 Go 编写、单文件分发，与后端 Go 技术栈同源，离线包只需多塞一个几十 MB 的二进制，契合强约束。
2. **可维护性强**：压测逻辑以 JS 脚本表达，可进 git 版本管理、可复用、可 diff，远优于 JMeter 的 .jmx。
3. **结果结构化**：k6 原生 JSON 输出（summary + metrics + 时序样本），后端可直接解析生成报告与阈值评估，无需自建采集统计层。
4. **适配层解耦**：抽象 `Engine` 接口（Generate/Run/Parse/Stream），避免与 k6 强绑定，未来可平滑接入 JMeter/Locust/自研，且 k6 升级只影响 Adapter 实现，不影响上层编排。

## 影响与取舍

- **影响**：k6 对"分布式大规模压测"的原生支持弱于 JMeter 的集群模式；若未来需要多机协同加压，需自行做水平拆分（多实例 + 结果聚合），或引入 k6 operator/Grafana k6 Cloud（离线不可用）。
- **取舍**：放弃 JMeter 的协议插件生态与 GUI；放弃完全自研的极致可控。鉴于首期目标是"接口级性能测试 + 阈值评估 + 报告"，k6 覆盖足够且集成成本最低。
- **可撤销条件**：若出现大量非 HTTP 私有协议压测需求，或必须多机分布式协同加压，可评估引入自研执行器或 JMeter 作为第二引擎（Adapter 层已预留）。

## 结论

压测引擎采用 **集成 k6（子进程 CLI）+ 引擎适配层**，自研仅作扩展兜底，兼顾离线、可维护与结果结构化。
