# ADR-0001：后端技术栈

- **状态**：已采纳（Accepted）
- **日期**：2026-10-26
- **决策者**：架构师
- **关联**：ADR-0002（前端）、ADR-0003（压测引擎）、ADR-0004（数据库）

## 背景

auto_performance 是一个性能测试平台，核心诉求不是"业务 CRUD 复杂度"，而是：

1. **离线部署**（强约束）：部署包必须自包含，目标环境可能无外网、无预装运行时。
2. **可移植、可维护**：迁移成本低，运维面小。
3. **并发与实时性**：一次压测任务会产生大量实时日志，需要以低开销将执行进度/日志推送到前端（WebSocket/长连接）。
4. **调度压测引擎**：后端需要以子进程方式拉起压测引擎（k6 等），解析其结果 JSON，并驱动报告生成。

## 备选方案

| 维度 | Go（Gin）✅ 推荐 | Java（Spring Boot） | Python（FastAPI） |
| --- | --- | --- | --- |
| 部署形态 | 单二进制，交叉编译 | JAR + JDK 运行时 | 解释器 + 依赖包 |
| 离线部署 | 极强（编译期打包依赖） | 弱（需内嵌 JRE，体积大） | 弱（需内嵌解释器+site-packages） |
| 并发模型 | goroutine，高并发低开销 | 线程池，开销可控 | 异步 + GIL（CPU 密集受限） |
| 压测调度/长连接 | 原生契合（net/http + WebSocket） | 成熟（WebFlux/Netty） | 可用（uvicorn/asyncio） |
| 内存占用 | 低（~几十 MB） | 高（几百 MB~GB） | 中 |
| 二进制/体积 | 小（10~30 MB） | 大（含 JRE 可上百 MB） | 中（含解释器可上百 MB） |
| 类型安全/可维护 | 强静态类型，编译期检查 | 强静态类型 | 弱（类型提示非强制） |
| 生态成熟度 | 中高 | 极高 | 高 |
| 团队门槛 | 中 | 中 | 低 |

## 决策

**采用 Go + Gin（HTTP 框架）+ go:embed（内嵌前端静态资源与报告模板）。**

- Web 框架选 `Gin`：路由/中间件/参数绑定成熟，性能好，社区活跃；`net/http` 标准库为兜底，避免过度依赖。
- ORM 选 `gorm` + 显式 `migrations`（`golang-migrate`），数据库迁移与升级脚本解耦。
- 配置使用 `viper`（YAML），支持环境变量覆盖。
- 日志使用 `slog`（结构化日志，标准库），统一输出到文件 + 控制台。
- 认证使用 `golang-jwt`，密码使用 `bcrypt`。

## 理由

1. **离线部署是首要约束**：Go 编译产物为单一可执行文件，可 `CGO_ENABLED=0` 交叉编译到目标平台（amd64/arm64），无外部运行时依赖；前端构建产物与报告 HTML 模板通过 `go:embed` 直接内嵌进二进制，实现"一个二进制跑起来"。
2. **压测平台天然契合并发与长连接**：goroutine 模型让"任务调度 + 日志推送 + 多任务并行"以极低资源开销实现，契合压测场景的高吞吐、高并发。
3. **可移植性强**：单文件部署，升级即替换二进制；运维面远小于 JVM/解释器方案。
4. **可维护性强**：静态类型 + 明确的包结构（internal/ 分层），长期维护成本低于动态语言。

## 影响与取舍

- **影响**：团队需具备 Go 能力；部分生态（如复杂报表 Word 生成）需借助少量第三方库（`unioffice`/`gooxml`）。
- **取舍**：放弃 Java 的生态纵深与成熟中间件集成能力；放弃 Python 的快速原型速度。鉴于本项目核心是"调度引擎 + 生成报告 + 平台化 CRUD"，Go 的收益显著大于代价。
- **可撤销条件**：若未来业务重心转向复杂业务编排/工作流（重 BPMN、重规则引擎），且团队以 Java 为主，可重新评估 Spring Boot。

## 结论

后端采用 **Go + Gin**，以单二进制 + go:embed 内嵌前端/模板，最大化离线部署与可移植性。
